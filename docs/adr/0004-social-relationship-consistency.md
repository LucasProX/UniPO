# ADR 0004 社交关系与私信的并发边界

状态：已接受，2026 年 10 月 22 日。关联 ADR-0001、ADR-0002、ADR-0003，工作包 DP03 与 DP14。

## 背景

先查询是否拉黑、再写关注或私信，不能保证两次操作之间关系不变。重复拉黑也可能在查不到记录后同时插入，撞上唯一约束。把两个用户行都加排他锁能串行，却会让热门用户不同关系的操作互相等待。

注销又是另一条写路径：它先置 deleted，再清理关注与拉黑。仅锁住用户对的迟到请求仍可能在清理完成后重新插入。实时投递和列表查询还可能沿用数据库旧快照或 MyBatis 查询缓存。

## 决策

V22 建立 `social_relationship_pair_locks`，规范为 low ID 小于 high ID，每个用户对一个唯一记录。关注、取关、移除粉丝、拉黑、取消，以及私信创建、历史读取和发送，在实际数据库事务中使用同一把锁。跨模块只暴露 `BlockQueryApi.lockPair`，不直接引用关系 Mapper。

获取锁前，按 ID 升序共享锁定双方用户当前状态，并要求 active，再取得 pair 锁。共享用户锁允许不同关系并行；注销持有用户排他锁直到清理提交，使关系写入要么先完成再被清理，要么等到注销后被拒绝。不得在持有 pair 锁后再反向申请用户锁。

社交与消息写边界采用 READ COMMITTED，避免不存在记录的锁定读在默认 REPEATABLE READ 下制造跨 pair 的间隙锁竞争。相同 pair 的幂等和一致性由显式关系锁及唯一约束保证。调用者不得通过更外层的旧事务快照弱化当前读。

对外的权威关系读取挂起调用方事务，并以禁用缓存的查询读取已提交事实。私信列表先取得候选、准备预览、用户和聚合未读，最后批量重查关系并过滤；未读总数也在数据库聚合后重查。不会对每个 peer 单独查库或持有全列表关系锁。

私信通知移到数据库提交后。回滚不投递，通知异常不改变已经提交的消息结果。当前回调不是持久 Outbox；DP14 继续承担提交后进程退出的恢复、重试和去重。私信不写入通用 replay，HTTP 消息接口是事实恢复入口。

## 保证与代价

同 pair 的创建、读取和写入按锁顺序串行。拉黑先提交时，等待它的私信必须拒绝；私信先取得锁时允许先完成。列表及实时帧以最终权威查询作为访问判定点，该点之后已进入传输的响应不能撤回。

额外成本包括关系锁记录、用户共享读锁和权威查询。不能由正确性测试推断热点竞争吞吐；DP23 需要测锁等待、连接池压力和端到端延迟。关系锁记录保留，清理不能任意删除正在使用的锁行，否则会产生两把锁保护同一个 pair。

暂停业务事务的查询可能额外占用一条连接，提交后同步通知也仍可能保留调用方资源。当前真实 MySQL 专项没有限制连接池大小，不能证明满池时的前进性。后续在 DP14 将通知移至独立 worker，并为持 pair 锁的检查提供不额外借连接的当前读；用小连接池专项验证后再评估发布。

## 验证

在独立 MySQL 中验证重复拉黑、关注交错、双向过滤、取消恢复、注销交错和事务回滚；在真实 Redis 中验证私信不进 replay。列表加载途中提交拉黑与旧快照读取要有门控测试。具体结果与未验 UI 项目见 DP03-VERIFICATION，不以本 ADR 的接受状态代替功能验收。
