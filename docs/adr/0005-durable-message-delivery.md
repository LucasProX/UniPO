# ADR 0005 持久消息投递与恢复

日期：2026 年 10 月 22 日。状态：已采用，实施验证中。关联 ADR-0001、ADR-0002、ADR-0004，工作包 DP14。

## 背景

提交后回调能避免数据库回滚却先送出私信，但消息提交与进程内回调之间仍有退出窗口。回调执行时也可能保留原事务连接，关系权威查询再借一条连接后，小连接池就可能互相等待。实时通知需要从 HTTP 消息写事务中分离，同时保留一份可恢复的投递事实。

## 消息与投递意图一起提交

V23 增加 `message_delivery_outbox`。`MessageService.send` 保存消息、更新会话时间，并经 `MessageOutboxStore.enqueue` 插入 REALTIME 和 PUSH 两条投递意图，全部使用原事务。enqueue 要求已存在实际数据库事务，不另开事务；任一写入失败会使本次业务事务失败。

每个消息与通道只有一条意图，唯一约束为 `(message_id, channel)`。每条意图有独立、稳定的 32 位十六进制 `event_id`；重复入队和投递重试不更换它。表内只保存消息 ID、状态、时间、尝试次数和安全错误码，不复制正文或设备 token。消息被物理删除时，外键只级联清理它自己的投递元数据；账号注销仍走已有软删除与隐私规则。

迁移不对历史消息回填通知。原有消息继续通过 HTTP 历史接口读取，不因部署新 worker 而重新推送旧提醒。

## 领取与租约

MySQL 的 `UTC_TIMESTAMP(6)` 决定可领取时间、租约、完成时间及重试时间。这些内部 UTC 字段不经客户端时间或 JVM 默认时区计算。

领取在 READ COMMITTED 的短事务内执行 `SELECT ... FOR UPDATE SKIP LOCKED`，只选择到期的 PENDING，或租约已过期的 SENDING。领取生成新的随机 `claim_token`、推进尝试次数并写入租约，提交并释放连接后才返回给 worker。尝试次数饱和在整数上限，不绕回负数。

完成、抑制、失败和重试均以 `id + claim_token + SENDING + 租约仍有效` 为条件更新。原 worker 即使在新 worker 重领后才返回，也不能完成或重置新的租约；没有被其他实例重领的过期租约同样拒绝旧确认。进程退出会留下可过期恢复的记录，不依赖内存 Map。

后台领取与状态操作拒绝在已有业务事务中调用，避免通过挂起外层事务额外占用连接。消息已经持有用户对锁时，关系检查使用同一连接的当前读；后台 worker 则在独立执行边界重新查询权威关系。网络调用期间不持有 Outbox 行锁或业务事务。

## Worker 与结果

独立单线程调度器默认每秒运行一轮，每轮最多处理 20 条。每次只领取一条，租约为 60 秒，避免批量预取后排在队尾的租约先过期。`MESSAGE_OUTBOX_ENABLED` 默认 true，轮询间隔默认 1000 毫秒，可配置范围为 100 至 60000 毫秒；关闭调度不会停止消息写入投递意图。

投递前重新读取消息、双方账号状态与双向拉黑关系。消息不存在、任一账号非 active 或任一方向已拉黑时，记录为 SUPPRESSED，之后取消拉黑不会补发这条旧提醒。消息事实的读取仍遵守独立的 HTTP 权限规则。

| 状态 | 含义 |
| --- | --- |
| PENDING | 等待首次尝试、重试时间或后续设备分片 |
| SENDING | 有实例持有效租约；过期后可被其他实例重领 |
| DELIVERED | 该通道的本次服务端投递工作完成，不代表设备收到、显示或已读 |
| SUPPRESSED | 按当前隐私或对象状态停止这条提醒 |
| FAILED | 不可重试的提供商结果，保留记录供受控处理 |

临时失败返回 PENDING，指数退避最多 300 秒，并与提供商要求的最短等待取较大者。永久失败写 FAILED。错误字段只接受稳定白名单代码，未知输入归一为 `DELIVERY_FAILED`，不保存原始异常、通知内容或设备凭据。FAILED 与未完成意图不自动删除；受控查询和重试工具仍需补齐。

REALTIME 与 PUSH 分别确认，某个通道失败不重做已经完成的另一个通道。实时消息负载增加 `eventId`，私信仍不进入通用 replay、不占 replay 序号；断线后的消息事实继续由 HTTP 同步。

## APNs 语义与设备进度

`PushService.send` 在提供商尝试结束后返回；可重试和永久失败通过仅含安全代码、重试属性及等待时间的 `PushDeliveryException` 表达。APNs 使用稳定的事件 ID 构造 `apns-id` 与 pending collapse ID。collapse 能合并仍待投递的提醒，不能撤回已经到达系统的提醒，也不构成操作系统恰好显示一次的保证。

没有设备 token，或使用未启用真实 APNs 的日志实现时，正常返回只表示没有待执行的外部投递；此时 Outbox 通道完成并不表示设备收到通知。真实 APNs 接受请求也不是用户设备送达或已读回执。

V24 的设备级进度已在隔离 MySQL 通过专项。`push_delivery_batches` 按事件绑定用户、首次处理时的最大设备注册 ID 和轮转游标；`push_delivery_receipts` 按 `(event_id, device_token_id)` 记录 ACCEPTED 或 INVALID。回执不外键关联设备注册，避免设备注销时抹掉已经完成的投递进度；回执随事件批次清理。两表只保留 ID、结果和内部 UTC 时间，不复制设备 token 或正文。

每次最多取 64 个仍属于原用户、位于快照范围且没有回执的设备，按 ID 顺序和持久游标轮转。每个外部调用前再次核验当前注册的 owner 与 token；提供商明确接受或明确拒绝无效设备后才记回执。当前页处理完而仍有目标时，`APNS_MORE_TARGETS` 表示继续分片，按零等待重新入队，不计为提供商失败。轮转使前页失败不永久饿死后页设备。

APNs 一次调用的网络等待共享 10 秒预算，数据库读取和写入仍受各自的连接池与查询超时约束，不能把整个端到端耗时宣称为严格 10 秒。当前实现为 5xx 等待至少 15 分钟，429 至少一分钟，暂时不可用与超时至少一秒；无效负载和其他不可重试拒绝保留 FAILED。最终结构与测试边界在 DP14-VERIFICATION 维护。

## 至少一次与客户端

外部发送与数据库确认不能组成同一事务。实例可能在提供商已接受后、Outbox 确认前退出；另一个实例会用原事件 ID 重试。租约有效性检查到真正外部发送之间也有在途窗口，已开始的调用不能被 CAS 撤回。设计采用至少一次投递，不宣称端到端恰好一次。

iOS 对有 `payload.eventId` 的事件使用最多 1024 个 ID 的内存缓存去重，不保存正文；无 ID 的旧事件保持兼容。断开与重连清空缓存，超出窗口的事件可能再次被处理，消息展示仍依赖消息 ID 与 HTTP 事实。接收与心跳捕获创建时的 socket 和连接代次，等待返回后再次校验，旧连接迟到帧不能进入新账号回调或污染其去重缓存。

## 可观察性与验证

Outbox 保留各通道状态、尝试次数、可执行时间、租约和稳定错误码；Micrometer 暴露积压、处理中、失败存量、最老等待时长以及完成、重试、继续、抑制和租约丢失计数。失败存量 Gauge 命名为 `unipo.message.outbox.failed.current`，避免与失败动作 Counter 的 Prometheus `_total` 导出冲突。指标不使用用户 ID、事件 ID、token 或正文作为标签。

验证覆盖同事务回滚、未提交不可见、双 worker 领取、租约过期与旧 owner CAS、独立进程退出后恢复、单连接池、通道独立失败和隐私抑制。V24 的设备归属、部分完成、分片与上下文重建续投已有真实 MySQL 证据，网络为替身。当前通过结果及未验项目见 [DP14 验收记录](../DP14-VERIFICATION.md)。
