# UniPO 总体产品分析与开发执行计划

> 基线日期：2026-10-21
> 状态：执行中的产品与工程路线图
> 目标：把 UniPO 从“功能较多的校园社区原型”推进为“一个学校、一个专业、一个年级可验证的大学成长产品”。
> 维护规则：完成任务时更新状态、验收证据和日期；需求改变时先更新本计划，再改产品与架构文档。

本文以仓库代码、现有文档和本轮只读审查为依据。代码现状不等于线上成熟度；凡涉及用户价值、留存、付费意愿和学校合作的结论，都必须由真实试点验证。

关联文档：[产品方向](PRODUCT-PLAN.md)、[架构快照](ARCHITECTURE.md)、[问题清单](ISSUES.md)、[API 参考](API.md)、[前端指南](FRONTEND.md)、[iOS 工程说明](../ios/README.md)、[平台 ADR](adr/0001-platform-baseline.md)、[模块边界 ADR](adr/0002-module-boundaries.md)。

## 1. 结论先行

UniPO 已有相当完整的工程底座：Spring Boot 模块化单体、MySQL/Flyway、MinIO、可选 Redis、Web Cookie + CSRF、iOS Bearer + Keychain、WebSocket、帖子游标分页、OpenAPI 类型契约和 CI 都已进入仓库。iOS 与 Web 的主界面、发帖、互动、私信和成就页面也已存在。

产品上的核心差距不是“功能不够多”，而是三个关键承诺尚未完整兑现：

1. **成长路线尚未可信地个性化。** iOS 首页阶段卡仍固定展示“大一上·第 3 周”、42% 和固定待办，容易让用户把演示内容当作个人真实进度。
2. **运营治理没有闭环。** 用户举报可以入库，但后台还没有完整的待处理队列、处置、申诉和时效管理；公开招募前需要先补齐。
3. **产品决策缺少行为数据。** 管理报表主要看新增用户和发帖；阶段卡、引导、任务、内容有效性、留存等事件没有形成可靠漏斗。

因此当前阶段的首要目标应是：**让目标新生在真实校园场景中，找到一条可信的下一步行动，完成它，并愿意回来。** 首页流量、工具、社交和游戏化都服务于这个目标；在价值和留存验证前，不扩张到金币经济、二手交易、付费或多校大规模拉新。

按百万日活设计是架构方向，不代表当前系统已通过百万日活性能验证。规模化前仍需压测、容量估算、监控告警和恢复演练。

## 2. 多角色评估

| 视角 | 当前判断 | 最重要的下一步 |
|---|---|---|
| 产品策略 | “大学四年的成长路线图”有区别度；当前外显体验仍主要是信息流与社交，路线图尚未成为可靠的每日价值 | 先验证一个学校、一个专业、新生群体的单条成长主线 |
| 系统架构 | 模块化单体、单一 API、状态外部化方向正确；Redis 与实时通道有关键边界需集成测试 | 修复/验证会话索引 TTL、WebSocket 续传与事务后事件投递 |
| 后端工程 | 帖子域已有批量查询与游标分页；私信全量读取、互动计数并发、密码重置吊销仍有风险 | 先解决身份吊销、消息可靠性和高增长查询路径 |
| iOS / Web | 主要页面已存在，iOS 有原生组件与视觉 tokens；多个页面仍有静态/占位行为，窄屏和并发分页需加固 | 让首页、工具、课表对用户展示的承诺与真实能力一致 |
| UI / 视觉传达 | iOS 个人主页已形成清晰的 paper / ink / blue 语言；Web 仍有不少散落颜色和高圆角/glass 样式 | 共建语义设计 tokens，维持品牌一致而不强求两端布局相同 |
| 运营 | 已定义主线/支线、金 V 和冷启动方向；内容更新、举报处置、学校合作交接仍缺可执行 SOP | 先建立内容核验、审核、过期复核和举报处置责任链 |
| 数据与增长 | 管理后台有基础运营报表；激活、留存、任务价值、内容质量无法可靠计算 | 建隐私最小化的事件目录和 cohort 漏斗 |
| 发布准备 | 后端与前端有构建/冒烟；缺少 Web/iOS 用户旅程自动化、正式协议验证、备份恢复演练 | 设立单校外部试点门槛，逐条验收后开放招募 |

## 3. 产品定位与目标用户

### 定位

**UniPO：大学的每一步，都有可信、可执行的下一步。**

帖子是经验和本地信息的载体；成长路径负责把这些信息组织成“什么时候、为什么、具体做什么”。用户应能从阶段任务进入相关攻略，再把自己的结果或补充经验贡献给下一位同学。

### 先服务谁

| 用户 | 当前最痛的任务 | 产品优先承接 |
|---|---|---|
| 大一新生 | 不知道报到、选课、社团、四六级从哪里开始 | 按学校/专业/年级生成的阶段卡、核验过的清单和攻略 |
| 高年级经验作者 | 经验散落在群聊，难被后来者找到 | 有模板、来源、适用范围和署名的经验 PO |
| 班委/社团负责人 | 通知触达、报名组织、换届交接 | 经认证的身份、活动/通知发布和可审计运营入口 |
| 校园运营 | 内容过期、投诉无人处理、数据说不清 | 内容审核、举报队列、内容有效期、cohort 报表 |

### 核心用户闭环

```text
选择学校 / 专业 / 年级
        ↓
看到此阶段的真实任务与可信来源
        ↓
阅读攻略 / 使用工具 / 完成一项行动
        ↓
记录进度，获得有意义的反馈
        ↓
回来完成下一项，或贡献一条可复用经验
```

发布、关注、私信、签到和徽章是辅助机制。它们不应抢走阶段行动的入口，也不应用纯发帖数量作为成长价值的替代指标。

## 4. 代码现状与产品落差

| 能力 | 仓库现状 | 判断与动作 |
|---|---|---|
| 首页 PO 信息流 | 已接真实接口、板块、轮播、帖子详情、评论、点赞收藏；后端有游标分页 | 保持为内容入口；首页同时需要一个真实、个性化的阶段行动入口 |
| iOS 阶段卡 | HomeView 固定展示第 3 周、42% 和固定待办 | 这是首屏信任问题，必须由用户阶段/成就 API 驱动；无数据时明确显示空态 |
| 成就与阶段任务 | 后端有阶段、任务、完成记录、徽章；iOS 有成长路径页面 | 自动完成规则、阶段个性化和任务内容质量需在试点前定义；不可用演示进度冒充真实进度 |
| 工具箱 | iOS 显示 5 个工具及“本地处理/每月 5 次”，点击仍提示接入中 | 首发只展示实际可用工具；隐私、额度文案必须与实现一致 |
| 课程表 | Web 有本地课程编辑；导入行为当前只是提示，依赖本地存储 | 首版明确 local-first 或账号同步；实现真实导入、冲突处理和导出，未实现的不要宣传 |
| 私信与实时 | WebSocket 已落地，轮询作为兜底；iOS 有消息列表与推送入口 | 需验证 Redis 续传序号、提交时序、长会话分页、前后台重连；不要把在线广播描述为可靠投递 |
| 举报与拉黑 | 有用户举报提交与拉黑能力 | 举报没有后台处置闭环；需要用户/帖子举报对象、状态、审计、申诉及拉黑后的内容过滤 |
| 管理后台 | 有概览、内容、轮播、用户权限、报表、监控、审计页面 | 部分设置页仍为占位；报表只有有限的新用户/发帖统计，不能支撑增长判断 |
| 分析事件 | analytics_events 有实体/Mapper，但没有形成业务事件写入流水 | 先定义事件和隐私边界，再做埋点与 cohort 报表；不要靠猜测数据做增长决策 |
| 协议与登录 | iOS 协议正文为占位，登录同意默认勾选；正式身份通道尚未完成 | 外部试点前完成真实条款、隐私说明、默认未勾选和未同意不可继续；明确 Release 登录方案 |
| 测试覆盖 | 后端单测、ArchUnit、CI 冒烟和构建已有；仓库未发现前端 E2E / iOS XCTest 核心旅程 | 增加关键用户旅程与设备/窄屏覆盖，CI 仅绿不代表体验完成 |

## 5. 工程与架构判断

### 已做对、应继续守住的边界

- 模块化单体优先，不提前拆微服务；跨模块通过 facade / api 收口，不跨域直接调 Mapper。
- Web 与 iOS 共用 /api/v1 业务契约，避免复制业务规则。
- Web 用 httpOnly Cookie + CSRF，iOS 用 Bearer + Keychain；不要把 token 放 URL 或本地明文存储。
- MySQL 管业务数据，Redis 管可共享状态，对象存储管媒体；单机与多实例都沿同一部署边界演进。
- Flyway 迁移只增不改；响应码、错误码和时间格式视作客户端契约。
- 上传校验信文件头；内容清洗和权限校验不得退化成前端约定。

### 本轮代码审查出的工程任务

下面的风险来自代码路径审查，实施前应先补针对性复现与测试。尤其 Redis Stream 的序号问题标为“需验证”，不能只凭静态推测直接更改协议。

1. **改密与会话吊销**：AuthService.resetPassword 更新密码，但未看到同步吊销 Web 会话和 App refresh/access。验收：改密后 Web 旧会话、旧 refresh 均不可继续使用；App access 有明确且有界的失效策略；改密/重置测试覆盖。
2. **Redis 用户会话索引 TTL**：续期单个会话时需检查用户会话索引 TTL 是否同步延长；否则活跃会话过期后可能无法被“退出所有设备”找到。Redis 集成测试模拟跨 TTL 活跃并验证全部被吊销。
3. **WebSocket 续传游标**：RedisRealtimeStore 用自增序号与 Redis Stream entry ID 的对应关系需实测。验收：重启/多实例/断线恢复后按协议续传，事件不重不漏；超过保留窗时客户端有可恢复的全量/增量同步策略。
4. **消息事务与投递**：发送消息事务提交前发布 WS/启动 APNs，需改为提交后投递或 Outbox。验收：DB 回滚不产生幽灵通知，推送失败有重试与去重。
5. **私信分页与查询量**：会话列表和消息历史不应全量加载。增加游标分页、数据库侧 last-message/unread 聚合或冗余，并用长会话测试限制查询与内存增长。
6. **互动计数并发**：点赞/收藏计数不能采用读-改-整行更新导致并发丢增量；使用原子更新或可重算派生值，并验证计数等于唯一互动记录数。签到重复提交也要以幂等结果处理。
7. **iOS 信息流并发**：末条触发 load-more 时加 in-flight 锁和游标保护，快速重复触发不重复 append、不漏条。
8. **Web 错误反馈**：feed 续页、评论/帖子刷新有 catch 后静默保留旧内容的路径。保留当前内容可以，但应给出非阻塞的重试反馈，不能让失败看起来像成功。
9. **用户域边界**：auth/user 仍分散于共享 service/web/domain/mapper；message 和 taxonomy 有共享用户依赖。按 ADR-0002 逐域迁移，先做 user facade，再逐步收回 mapper 所有权；每次只迁一个域。

## 6. 视觉与交互设计执行准则

### 品牌语言

- 延续 iOS 已建立的 paper 画布、ink 信息、blue 行动强调；gold 仅用于稀有奖励或关键成长结果，不让所有页面都变成蓝色大渐变。
- Web 和 iOS 共享语义 tokens（品牌色、正文/次级文字、成功/警告/危险、间距、边框、焦点状态），但保留各自平台原生布局与交互。
- 面向重复操作的后台采用紧凑、清楚、可比较的工作界面；内容浏览页可有编辑感，但避免玻璃面板、阴影、超大圆角层层叠加。
- 任何装饰都应服务内容辨识；阶段、来源、风险、是否过期靠稳定标签和图标表达，不用无意义光效替代层级。

### 页面层级

| 页面 | 第一层信息 | 主要动作 | 视觉 / 交互要求 |
|---|---|---|---|
| 登录与引导 | 为什么选学校/专业/年级，下一步会得到什么 | 完成必要资料、选择隐私选项 | 少量步骤、可跳过非必要资料；协议默认不勾选；错误可恢复 |
| 首页 | 当前阶段的一项真实下一步，其次才是校园内容 | 打开任务/攻略、继续信息流 | 阶段卡不能用假进度；显示适用学校/专业/年级、更新时间和来源 |
| PO 信息流 | 内容类型、作者身份、相关性和时间 | 阅读、保存、评论、举报 | 卡片可快速扫描；官方/学生经验有清晰区分；错误、空、加载、离线状态一致 |
| PO 详情 | 解决的问题、关键结论、经验来源 | 保存/反馈有帮助/参与讨论 | 长文分段、图片可访问、评论与举报入口可发现 |
| 发 PO | 用户正在分享什么经验，适用谁 | 发布、存草稿 | 提供“问题-做法-结果-适用范围”轻模板，不强迫写长文 |
| 成长路径 | 当前学期/阶段、已完成与下一项 | 完成任务、查看攻略 | 任务可执行且有结果定义；进度可解释；不靠虚假倒计时或强制连续签到 |
| 工具箱 | 当前真正可用的本地工具 | 选择文件并完成处理 | 处理位置、隐私、额度和失败边界都准确；未开放功能隐藏或清楚标注 |
| 个人主页 | 身份、关系、作品 | 关注、查看作品、编辑资料 | 保持已有“身份 → 关系 → 内容”层级；尊重用户资料可见性开关 |
| 运营后台 | 待办、风险和需要处理的对象 | 审核、处置、留痕 | 可筛选/批量处理/回查；高密度表格优先；每个状态有明确空/错/成功反馈 |

### 视觉系统与体验验收

- 把 iOS UniPOUI tokens 映射到 Web CSS variables / Tailwind 主题，不复制一份无法同步的颜色常量。
- 统一按钮高度、焦点环、输入错误、禁用、加载、空状态和危险操作确认的规范；图标按钮有 tooltip / accessibility label。
- Web Dock 必须在 320、375、390、768、1440 px 检查，不允许固定宽度导航溢出；桌面侧栏在平板/手机有明确折叠规则。
- iOS 覆盖 iOS 17 基线、Dynamic Type、VoiceOver、Reduce Motion、键盘焦点、44pt 触控区域和深浅色/高对比度检查。
- 不以“视觉一致”为由把 Web 改成 iOS 仿版；共享品牌语义，分别遵循浏览器与 iOS 的导航习惯。
- 每个核心页面至少验收真实数据、无数据、加载中、接口失败、弱网/重试、长文本、窄屏和登录过期状态。

## 7. 运营、内容与治理

### 内容生产标准

每条攻略或任务内容至少要有：适用学校、学院/专业（允许通用）、年级/学期、问题、可执行步骤、来源类型、核验人或来源链接、最后核验时间、失效/复核时间。官方信息与学生经验要分开标记，不把个人经验包装成学校官方事实。

内容分三层：

1. **主线**：平台维护的通用成长节点，需标注适用范围与版本。
2. **学校/专业支线**：校园运营或作者本地化，校运营审核、平台抽查。
3. **即时信息**：活动、报名、时间变更，必须有明确失效日期，过期自动下架或转待核验。

### 单校运营组织

- 平台负责人：确定内容标准、处理升级投诉、维护合作关系和月度复盘。
- 校园运营：负责本地事实核验、金 V 初审、活动与内容更新。
- 学生作者：按模板提供具体经验，来源和适用范围清楚；身份认证材料不公开。
- 账号与内容资产归平台账号体系管理；交接清单不能依赖某一个学生私人群或个人账号。

### 周运营节奏

- 每周复核近期会过期的通知/报名/政策内容。
- 每周发布若干条有明确场景和下一步的本地内容，优先覆盖新生当前周期；数量按人员产能定，不以凑条数为目标。
- 收集用户“有帮助/没解决”反馈，找出路径中无人能回答的节点，再补作者或官方来源。
- 复盘举报积压、误伤申诉、内容撤回、金 V 到期和运营权限变更。
- 活动、群聊和二维码拉新必须能归因到渠道，但分析事件不得记录帖子正文、私信正文、手机号、验证码或 token。

### 举报处置闭环

外部试点前必须具备：举报用户和单条帖子；原因分类与补充说明；后台待处理、处理中、已处理/驳回状态；处理人、时间、证据和结果审计；用户拉黑后双方内容/消息规则一致；申诉入口；按严重度设值班时间与响应时限。高风险内容应有升级路径。没有可执行的处置责任人时，不开放公开投稿与大规模拉新。

## 8. 数据指标与实验

### 北极星

沿用产品规划的 **Weekly Active Progressors（每周活跃成长用户）**：每个 ISO 周至少完成一项有效阶段任务的去重用户数。后台只把服务端确认的任务完成作为分子，不把打开页面或领徽章算作完成。

### 漏斗定义

| 阶段 | 建议定义 | 需记录的事件 |
|---|---|---|
| 来源 | 通过带 campaign/source 的校内链接或二维码进入 | landing_viewed, referral_opened |
| 注册 | 账号建立成功 | signup_completed |
| 激活 | 注册 24 小时内完成 onboarding，并打开个性化阶段任务 | onboarding_completed, stage_viewed |
| 价值 | 完成第一项阶段任务，或对攻略给出“有帮助”反馈 | task_completed, guide_helpfulness_submitted |
| 留存 | 同一注册 cohort 在第 1/7/30 日回访；同时观察每周活跃成长用户 | cohort_returned |
| 贡献 | 发布可复用经验、收到有效帮助反馈或被运营采纳 | post_published, post_helpful, content_adopted |
| 治理 | 举报创建、首响、结案、超时与申诉 | report_created, report_acknowledged, report_resolved, appeal_resolved |

### 事件数据边界

事件目录需要 schema version、事件 ID、发生时间、内部 user ID、school/major/cohort、必要对象 ID 和来源渠道。不得采集正文、私信内容、密码、验证码、access/refresh token 或可直接识别个人的冗余字段。按用途限定保留期限，并向用户说明分析用途。服务端任务完成与客户端页面浏览分开记录，以便核对丢失和重复事件。

### 试点指标

PRODUCT-PLAN 中的“500 注册、D7 ≥ 30%、首个任务完成 ≥ 30%”保留为**待验证假设**，不是已实现成绩。启动计数前明确注册 cohort、分母、7 日窗口、跨设备去重和无效/测试账号过滤。同步看内容新鲜度、每个关键任务可用攻略覆盖率、投稿有效率、举报处理时效和用户访谈，不因单一留存数字优化成强推送或无意义签到。

## 11. 主要风险与控制

| 风险 | 早期信号 | 控制动作 |
|---|---|---|
| 核心路线被信息流吞没 | 浏览很多但任务完成少 | 首页突出一个真实下一步；以 WA Progressors 而非停留时长观察 |
| 静态/假数据损害信任 | 年级不匹配、完成率固定、工具点不开 | 生产路径禁止假数据；能力未上线不展示承诺 |
| 内容过期或来源混淆 | 报名结束仍排在推荐位 | 强制来源/核验日期/有效期，过期自动降权或隐藏 |
| UGC 治理缺位 | 举报积压、被举报内容无人负责 | 先做举报后台、审计和升级排班，再做公开拉新 |
| 多端行为不一致 | Web 与 iOS 相同操作结果不同 | 共用 API/规则；用跨端旅程契约测试，不强制视觉布局相同 |
| Redis 或消息异常静默 | 多实例状态不一致、断线丢消息 | 集成测试、请求 ID、告警、Outbox/可恢复同步 |
| 单人/学生运营换届 | 账号、内容、合作关系随个人消失 | 平台归属账号、组织级文档、学期交接与审核权限审计 |
| 提前商业化 | 用户还没完成有效任务就出现收费 | 先证明连续 cohort 的任务价值和留存，再评估支付 |
| “百万日活”被误读为已具备容量 | 没有压测却宣传规模能力 | 对外只报告实际压测/SLO，架构目标和已验证容量分开写 |

## 12. 暂不做的事

- 不拆微服务，不同时开发 Android，不按客户端复制业务 API。
- 不先做支付、云盘、二手交易、金币商城和复杂等级经济。
- 不因为“运营后台应该有”就堆静态设置页；每个设置项必须对应真实流程和责任人。
- 不用下载量、注册数、屏幕停留时间代替阶段价值；不奖励纯发帖量。
- 不在没有真实校园合作、内容来源与审核资源前启动大规模校园推广。
- 不把 Redis Pub/Sub 在线广播描述为持久可靠的消息队列。

## 13. 开发节奏与 Definition of Done

每项工作按“用户问题 → 可观察行为 → 数据/API → UI 状态 → 测试 → 运营手册”闭环交付。

- 产品任务：有目标用户、触发场景、成功结果、空/错/未授权状态和是否采集数据的说明。
- 后端任务：权限、并发、幂等、错误码、Flyway 和 API 契约明确；跨域遵守 ADR-0002。
- Web/iOS 任务：真实数据，不新增假兜底；有加载/失败/空态；窄屏、最低系统版本、无障碍考虑到位。
- 发布任务：自动化测试通过；对安全、支付成本、用户通知或生产数据的影响可审计；运行/恢复说明已更新。
- 数据任务：事件 schema 有版本，不含敏感正文；仪表板展示 cohort 和分母，能从原始数据复算。
- 每周复盘：更新本文件中对应任务和验收链接；发生关键取舍时同步 ADR / DEVLOG，避免重复追查。
