# UniPO 项目审查与下一步清单（2026-10-24）

> 视角：董事长 / 产品经理 / 设计师 / UI 设计师 / 工程师。
> 范围：iOS、后端、基础设施的当前代码与文档（截至提交 `a41dd4a`）。
> **不含**正式上线才做的事：公网域名与 HTTPS（R01）、正式短信（R02）、告警值守（R05）。
> 依据是实际读代码与在模拟器里看到的结果，引用的文件都可以点开核对。

---

## 0. 一页结论

**方向没有跑偏，但重心在悄悄偏向「校园社区」。** 最近两周交付的功能（活动签到、成长三段、关注流、搜索、私信、联动）质量都不错，可它们大多在加强「社交和信息流」这一层；产品规划里真正的核心——「大学四年的成长路线图」和北极星指标「每周完成至少一个阶段任务的人数」——在首页已经看不见，内容也还是平台通用稿，没有一条来自真实学校。

三件事决定接下来能不能找真人试点：

1. **真实内容**：没有一所学校、一个专业的真实主线（G01），成长页、搜索、联动都没有东西可展示。这是最大的瓶颈，而且只有你能提供原始资料。
2. **治理底线**：目前只能举报「用户」，不能举报帖子和评论；没有违禁词过滤；发帖即时公开。这既是试点风险，也是 App Store 对 UGC 应用的硬性审核要求（举报、拉黑、过滤三件套）。
3. **基础自助能力**：引导完成后**改不了昵称、简介和隐私开关**，拉黑了也**没有地方解除**。真人用一天就会碰到。

做完这三件，再补「首页成长钩子」和「截止提醒推送」，就具备了 30–50 人封闭试点（P03）的条件。

## 1. 是否偏离核心（董事长 / 产品经理）

| 规划里的核心 | 现在的实际情况 | 判断 |
|---|---|---|
| 定位「成长路线图」，信息流只是功能（[PRODUCT-PLAN §4.1](PRODUCT-PLAN.md)） | 首页只有信息流（2026-10-23 按你的决定移走了学期卡和本周活动），成长在第二个 Tab | ⚠️ **最需要讨论的一条**，见下文 |
| 「入口必须被设计出来，不能靠运气」（§4.2） | 首页没有任何成长提示；成长 Tab 没有角标；没有截止前推送 | ⚠️ 成长靠用户自己想起来去点 |
| 主线由平台写、支线由学校/学长写，带来源（§6.7） | 主线是「UniPO 编辑部整理」的通用稿；来源字段、复核日期、版本都做了（G05/G06） | ✅ 结构到位，⚠️ 内容空 |
| 成长奖励只来自可验证的事（§6.3） | 只有认证组织者的活动发经验与金币，个人计划不发奖励 | ✅ 守住了，这是项目最有价值的设计之一 |
| 金币「有来源也有消耗」（§6.4） | 只能通过活动赚，**没有任何地方能花** | ⚠️ 没有出口的货币会让用户困惑 |
| 社交是留存层，不是品牌（§5.5） | 关注流、搜索、私信、互动通知都已齐 | ✅ 程度合适，别再往「校园小红书」方向加 |
| 第一年不做二手交易（§2.3） | 我上次的功能建议里列了「二手」 | ❌ **我建议撤回**，和规划冲突，且有交易纠纷与合规成本 |
| 工具箱是「让你有理由装它」（§1） | 已暂停（你的决定） | ➖ 可以，但要接受「装机理由」只剩活动和内容 |

### 关于首页

你移走学期卡的理由（首页干净、只看帖子）是成立的，我不建议把原来的大卡片放回去。但北极星指标是「每周完成阶段任务的人数」，如果首页和推送都不提醒，这个指标只能靠自然打开成长页，试点数据大概率会很难看。建议三选一或组合（需要你拍板，见清单 F07）：

- **A. 成长 Tab 角标**：本周有到期任务或活动时，底栏「成长」显示小红点。成本最低，完全不改首页。
- **B. 信息流插卡**：在第 4 条帖子后插一张窄卡「本周该做：四级报名（周五截止）」，可关闭，一周最多出现一次。
- **C. 截止提醒推送**：任务和已报名活动截止前 24 小时推送。依赖真机推送证书（M05）。

我的建议是 **A + C**，首页保持纯净。

## 5. 要优化的架构（工程师）

| 编号 | 问题 | 证据 | 建议 |
|---|---|---|---|
| E01 | **user 模块还没收口** | 用户、关注、拉黑仍在共享的 `domain/` `mapper/` `service/` `web/`；post、activity、achievement、growth、message 都直接注入 `UserMapper`；这次关注流也直接查了 `user_follows`（`PostService.followingFeed`，是我留下的债） | 建 `user` 模块，对外只给 `UserQueryApi` / `FollowQueryApi`，其他模块不再碰用户表 |
| E02 | **领域事件一处都没有** | ADR-0001 规定「跨模块走 facade + 领域事件」，代码里 `@TransactionalEventListener` / `ApplicationEventPublisher` 为 0；发帖时在同一事务里同步给最多 2000 个粉丝写通知 | 改成提交后事件 + 异步处理，可以复用私信已有的持久 Outbox 模式 |
| E03 | `PostService` 1298 行 | 信息流、搜索、关注流、互动、评论、发帖、通知都在一个类里 | 按查询、互动、写入拆成三个服务，facade 不变 |
| E04 | **图片没有缩略图** | 发帖图最长边 2048 的 JPEG 原图直接用在信息流卡片上；iOS 用 `AsyncImage`，没有磁盘缓存，滑回来会重新下载；图片经后端从 MinIO 转发 | 上传时生成列表图（约 600px）和详情图（约 1200px）；iOS 配大容量 `URLCache` 或自建图片缓存；量大后改预签名直连或 CDN |
| E05 | 推荐排序与计数 | 无时间衰减（见 F08）；`/posts/boards` 每次做 4 个 `count(*)` | 加 `hot_score` 列定时刷新；板块计数缓存或去掉 |
| E06 | `riskLevel` 由客户端决定 | `PostService.java:287` 直接取请求里的值 | 改为服务端根据过滤结果决定（和 F02 一起做） |
| E07 | iOS Feature 层大文件、零测试 | `ProfileView` 862 行、`GrowthPlanViews` 761 行、`PostDetailView` 688 行；Core 有 128 个测试，Features 没有 | 把状态逻辑抽进 Core 的 Store（参照 `FeedStore`）再补测试；大视图按区块拆文件 |
| E08 | 搜索的扩展边界 | MySQL ngram 单校够用；生产库第一次建全文索引会重建整表 | 生产执行 V34 前评估表大小并选低峰；多校后再评估 OpenSearch |
| E09 | 测试与 CI 可见性 | 127 个隔离 MySQL / Redis 专项默认跳过；本机没装 `gh`，看不到 CI 最近状态 | CI 定期跑隔离专项；装 `gh` 或在发布清单里加一步「确认 CI 绿」 |
| E10 | 测试与生产同机 | 4C4G 服务器同时跑生产与 test 两套后端和两个库 | 试点前确认内存余量；有条件把 test 挪到另一台 |
| E11 | 跨端契约 | Web 暂缓但 `api-types.ts` 仍要每次重生成 | 保留，成本很低，能防止契约悄悄漂移 |
