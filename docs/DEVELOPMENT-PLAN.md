# UniPO 开发规划书

版本：1.0　基线日期：2026 年 10 月 21 日　适用范围：单校试点版本至可复制版本

面向：产品负责人、设计、后端、iOS、Web、测试、基础设施与校园运营。本文规定后续开发的交付范围、先后依赖、工作量假设和验收方式。所有排期、资源、试点规模与指标阈值均为规划建议，按实际人力与试点反馈调整。

本期目标是让一所学校、一个专业、一个年级的学生完成真实成长任务，并使团队能够维护内容、处理举报、解释数据和恢复服务。iOS 为主要使用端，Web 承接分享、阅读、轻量任务与管理后台。先完成安全与治理底线，再验证成长闭环和一个本地工具，最后根据连续试点数据决定扩展。

## 1 项目目标与开发原则

### 1.1 需要交付的用户结果

学生首次进入时能理解 UniPO 提供什么，选择必要的成长背景，看到当前适用的一项行动，阅读可靠攻略并记录完成。下次进入时，阶段、任务和进度保持一致。学生分享的经验能够被后来者找到，过期或有问题的内容能够被运营及时处理。

首个试点版本以五条用户旅程验收：访客阅读分享内容；登录并完善成长背景；查看并完成任务；使用图片转 PDF 并导出；提交举报并收到处理结果。私信、发 PO、收藏和个人主页沿用已有能力，补齐可靠性与错误恢复。

### 1.2 必须守住的约束

- 延续 ADR-0001 与 ADR-0002：模块化单体、共用 `/api/v1`、SwiftUI 原生 iOS、状态外部化；单台服务器必须可完整运行。
- Web 使用 httpOnly Cookie 与 CSRF；iOS 使用 Bearer 与 Keychain，URLSession 禁用 Cookie。
- 按百万日活的方向保留扩展边界；对外报告的容量只能来自实际测量。
- 生产界面只展示真实能力和数据；无匹配内容、无网络、未完成引导必须各自有明确状态。
- 设计、内容、数据和运营与功能一起交付；每个工作包都有可观察的验收结果。

### 1.3 文档职责

本规划书作为本期范围、排期、工作包和验收的维护入口。[PRODUCT-PLAN](PRODUCT-PLAN.md) 保留长期产品方向，[PRODUCT-EXECUTION-PLAN](PRODUCT-EXECUTION-PLAN.md) 保留审查分析和风险来源。两份旧文档中的阶段名称和愿景清单不直接等于本期承诺。

任务进度在本文工作包中维护；接口事实写入 API，技术取舍写入 ADR，排障与经验写入 DEVLOG。Word 版由本文生成，变更时一起更新，避免形成两份互相矛盾的计划。

## 2 现状基线与主要缺口

### 2.1 已有能力

仓库已有 Spring Boot 后端、MySQL 与 Flyway、MinIO、可选 Redis、Cookie 与 Bearer 双认证、WebSocket、帖子游标分页、OpenAPI 类型断言、管理后台和 CI。iOS 已有登录、引导、信息流、帖子详情、发布、私信、成就和个人主页。

这些能力说明项目具备继续开发的基础；不代表所有端到端流程已通过外部试点或正式发布验证。管理员初始化凭据加固已提交并推送，基线提交为 `38c516b`；分析文档提交为 `45f5f67`。

### 2.2 本期需要补齐的差距

| 领域 | 基线事实 | 本期交付结果 |
| --- | --- | --- |
| 成长背景 | iOS 引导尚无学校与专业选择 | 增加学校、专业及入学年份或阶段，允许修正 |
| 阶段匹配 | 当前阶段依赖首个未完成阶段；首页有固定第 3 周与 42% | 按实际背景与校历匹配，进度可解释，无匹配时明确说明 |
| 任务内容 | TaskView 尚缺来源、期限、适用范围和关联资源 | 完整任务详情、内容版本、来源与复核机制 |
| 工具 | 有入口，实际处理能力未接入 | 先上线图片转 PDF；其他入口收起或标注未开放 |
| Web 承接 | 帖子详情用弹窗；缺独立任务及分享路由 | 可直接访问的帖子和任务链接，登录后返回原处 |
| 治理 | 可提交举报，缺完整后台处理与申诉 | 举报队列、处理、审计、回执、申诉及值守 |
| 可靠性 | 会话吊销、Redis 索引、事务投递和计数有风险待验证 | 针对性复现、修复与真实依赖集成测试 |
| 发布 | iOS 工程仍有 localhost 与开发签名配置 | 区分开发与 Release，验证 HTTPS、签名、真机与推送 |
| 数据 | 有分析表，尚无完整事件流水与漏斗 | 可复算的激活、任务、留存和治理指标 |
| 设计 | 有 iOS Theme 与主页样式，Web 语义尚未收口 | 共享语义与组件状态，保留平台和主页特定规则 |

### 2.3 需要先核实的风险

会话索引续期、WebSocket 序号与 Stream ID、消息提交时序、计数并发等来自静态审查。开始修改前先写能稳定复现的测试，不把推测直接当成已确认故障。CI 已执行 `bash scripts/smoke.sh`，但跳过上传；本地上传、最低 iOS 版本和真机验证仍需独立完成。

## 3 版本范围与交付边界

### 3.1 版本分层

| 版本 | 使用对象 | 必须完成 | 进入条件 |
| --- | --- | --- | --- |
| 内部 Alpha | 团队与少量受邀测试者 | 真实登录、成长资料、动态阶段、任务与错误状态 | 关键权限测试通过，演示值不进入实际用户路径 |
| 封闭 Beta | 单校 30 至 50 名种子用户 | 治理闭环、一个工具、分享落地、核心埋点、恢复能力 | 试点前全部阻断项清零，内容和值守到位 |
| 单校验证版 | 分批扩到约 100 名，再评估 300 至 500 名 | 核心体验稳定、数据可核对、内容持续更新 | 两个连续小批次无未关闭严重问题，运营承载允许 |
| 可复制版本 | 第二专业或学校 | 模板、配置、隔离、交接和容量证据 | 试点价值成立，新增学校不依赖临时硬编码 |

人数是观察与运营安排，不是必须完成的拉新配额。每批次开放前复核质量，不因日期到了自动扩大。

### 3.2 本期范围

优先交付成长背景、阶段匹配、任务详情与完成记录、关联攻略、内容有效期、图片转 PDF、账号安全、举报与拉黑、Web 分享回流、关键消息可靠性、埋点、备份与发布配置。既有帖子、评论、收藏、个人主页保持可用并处理阻断缺陷。

课程表首版建议明确为 Web 本机保存，提供字段说明、手工编辑与备份导出；若暂不实现导入，则隐藏导入成功的假动作。跨设备同步、教务抓取和 iOS 原生课表另立需求。

五工具齐发、工具配额、金币账本、商城、付费、云盘、二手交易、附件平台、复杂活动与金 V 全套审核、Android、微服务不进入本期必交范围。真实身份认证与贡献奖励分别定义，不以投稿奖励冒充校园身份认证。

### 3.3 范围控制

遇到进度压力时，先削减装饰动效、完整深色主题、次要工具、课表导入和高级报表；保留成长闭环、身份安全、举报处置、数据真实性和恢复能力。若关键安全或消息可靠性无法按期验收，顺延试点，或关闭对应未验收能力后重新评审范围。

## 4 用户旅程与信息架构

### 4.1 主要使用路径

成长路径：访客浏览 → 登录 → 选择学校与专业及阶段 → 首页下一步 → 任务详情 → 攻略或工具 → 记录完成 → 返回真实进度。

内容路径：分享链接 → Web 阅读 → 可选登录收藏或参与 → 返回原内容；App 已安装时可进入对应页面，未安装时继续 Web 阅读。

治理路径：内容或用户菜单 → 举报原因与说明 → 受理回执 → 运营处置 → 用户查看结果 → 必要时申诉。

### 4.2 导航方案

iOS 保留首页、工具、成就、我的等现有核心入口，发 PO 为突出操作，消息从首页入口进入。未登录点我的仍触发登录，并在完成后进入个人主页。通过通知、分享或登录跳转进入时，返回栈需能解释当前页面来自哪里。

Web 优先建立 `/p/:id` 帖子详情和 `/tasks/:id` 任务详情等独立地址，具体路由名在实现时确定。保留桌面信息流与后台效率，手机端提供可阅读、可操作的响应式页面。登录后恢复原链接，内容被删除或不可见时给出明确原因及返回入口。

### 4.3 跨端行为约定

同一任务的适用范围、完成记录、撤回结果和权限由服务端定义，两端不各算一套。纯本地工具文件不上传业务服务；Web 本地课表不承诺与 iOS 同步。不能提供的跨端能力应在界面上说明。

## 5 功能规格与验收条件

### 5.1 登录与成长背景

首版应明确一个可上线的真实登录通道。现有账号与验证码能力、手机号入口、开发演示入口分别梳理；当前非 mock 短信发送仍返回未配置，不能默认供应商已接通。Release 配置不得依赖 DEBUG 演示号码。条款与隐私内容由产品负责人组织确认，客户端展示版本和入口，同意状态初始未选中。

成长必要字段为学校、专业或通用范围、入学年份或明确阶段。学院按学校字典关联，年级由规则计算或由用户确认。性别、出生年、MBTI、星座、头像等是可跳过的个人资料，不作为获取成长内容的强制条件。找不到专业时允许选择通用路径或反馈，不替用户默认大一。

验收：登录失败能重试；验证码限流有提示；资料保存失败不丢输入；更改背景后重新匹配路径且保留历史完成记录；不匹配的旧任务不计入新阶段分母；登录后返回此前任务或内容。

### 5.2 首页与动态阶段卡

首页优先显示当前适用的一项下一步，最多列三个待办，并展示进入任务与成就的入口。阶段卡显示适用范围、阶段依据、完成数与总数；没有学校校历时不显示虚构的第几周。消息未读、信息流与轮播保留已有功能，不挤压主要行动。

匹配规则建议依次读取用户背景、学校学期日历、已发布有效路径和任务适用范围。无校历但有通用路径时显示学期或阶段；无适配路径时说明当前覆盖范围。规则在后端统一实现，不用首页字符串拼接代替。

验收：大一与高年级测试账号看到各自数据；访客、待引导、无匹配、全部完成、首载失败和续页失败均有状态；快速触发分页只发一个同游标请求；重新进入时进度与服务端一致。

### 5.3 成长任务与完成记录

每个任务展示标题、解决的问题、步骤、适用范围、完成条件、时间窗、来源、核验时间、关联攻略与工具。任务可标记暂不适用；过期任务停止作为下一步推荐，但历史记录可查看。路径变更需要内容版本，不能悄悄改变用户已完成任务的含义。

完成方式区分用户自报和系统事件。报名、阅读准备、线下行动可由用户自报；上传、发布等系统内行为可自动记录。普通任务不要求学生证、成绩或截图证明。界面和报表称为完成记录，不宣称客观证明了能力提升。

验收：重复完成请求只产生一条有效记录和一次奖励；撤回后进度重算且规则明确；任务下架或版本变更后历史可解释；跨端结果一致；若有经验值变动，完成与撤回都能追溯。有效分母仅包含当前适用且发布的任务。用户自报暂不适用时不发奖励，并显示排除数量与原因；已完成任务需先撤回再排除，保留历史，避免靠缩小分母制造成长结果。

### 5.4 PO 内容与分享回流

保留信息流、发布、评论、点赞、收藏和主页作品。经验发布提供轻模板：问题、做法、结果、适用范围。官方来源、运营整理与学生经验用文字标签区分；过期、待核验、撤回和下架各有状态。作者身份不自动等于内容事实已核验。

增加任务关联 PO、内容有效期与帮助反馈。分享页面可匿名阅读允许公开的内容，按原权限控制评论、收藏和非公开内容；不为分享而扩大原数据可见性。动态预览和搜索收录的具体范围在公开发布前单独验收。

验收：直接打开链接不依赖此前浏览状态；登录后返回同一对象；正文与图片上传失败不丢草稿；重复点击发布不产生重复帖；下架、删除、拉黑、权限不足和网络失败均可辨识。

### 5.5 图片转 PDF 工具

建议先在 iOS 交付本地图片转 PDF：选择照片或文件、排序、删除、预览、生成、系统分享与保存。后续在 Web 对齐同一用户任务。试点免费使用，不先接金币和配额。内存与文件数量上限由真机测试确定，界面在处理前提示。

文件留在设备内处理；分析事件只记录开始、成功、错误码与必要的文件数量区间，不传原图、文件名或生成内容。取消应可返回，不产生成功统计；临时文件有清理规则。

验收：单图、多图、旋转方向、大图、权限拒绝、格式不支持、内存压力、处理取消和导出失败均有测试；飞行模式可完成支持格式的处理与导出；用户取消不显示处理失败。

### 5.6 消息与通知

对会话与历史消息增加游标分页和页大小上限；会话首屏不遍历所有历史。发送展示待发送、已由服务端保存、失败可重试状态；若没有回执协议，不显示未经确认的已送达或已读。

DB 写入与 Outbox 在同一事务完成，提交后由 worker 投递 WebSocket 与 APNs。采用可重试投递和事件 ID 去重；推送只是提醒，客户端通过 API 同步事实。超过实时续传保留窗口后明确要求重新同步，不承诺无限补发。

验收：回滚不产生幽灵消息或推送；提交后进程退出仍可恢复待投递事件；断线、重连、前后台切换和多实例不丢最终消息；重试不重复展示；退出和注销后连接与通知归属正确。

### 5.7 我的与账号控制

保留已确认的浅色杂志风和身份、关系、作品层级。资料可见性开关由服务端保存并用于他人主页。换头像继续使用系统导航栏的裁剪流程；上传失败回显，不静默使用旧图完成引导。

统一退出当前设备、退出所有设备、改密、重置、封禁和注销的身份失效规则。首发目标是这些操作完成后，既有 Cookie、refresh 和 access 在规定校验点失效；具体 auth version 或撤销策略需 ADR 与测试确认，不假定纯 JWT 可以自行立即失效。

验收：两设备与两实例分别测试旧凭据失效；失效动作成功后的下一次 API 请求和 refresh 必须拒绝旧身份。已建立 WebSocket 在 DP02 规格确定的最长间隔内关闭或拒绝上行，且停止投递私密事件；该间隔需给出明确秒数并验证。封禁、角色变更同样不能长期沿用旧权限；资料隐私在访客与他人账号下生效；注销软删除与匿名化不破坏帖子外键；退出后不继续展示私人缓存。

### 5.8 运营后台与举报

后台先补待处理队列、对象详情、筛选、指派、处理理由、证据快照、审计、用户回执与申诉。内容管理增加来源、适用范围、核验日、复核日和失效状态；成长任务内容使用版本与发布状态。试点期允许受控导入和审核发布，不要求先做完整 CMS。

举报采用待受理、处理中、已处理或驳回等状态，申诉独立关联原处理单。并发处置使用版本校验；重复举报关联案件而非简单删除。各角色只能处理授权范围的对象，跨校越权必须拒绝。

验收：运营能完成真实举报从创建到结案再申诉的旅程；所有处置记录操作者、时间、对象、理由和前后状态；用户看到有限结果，不暴露举报人或内部证据；无权和冲突操作返回稳定错误码。

## 6 UI 与视觉设计计划

### 6.1 设计方向

延续 paper 画布、ink 文字和 blue 行动强调。iOS 已有色值为 paper `#F7F8FB`、ink `#0B0F17`、blue `#2F6BFF`，来自 UniPOUI Theme。以清晰的文字和信息层级承载可信度，gold 用于少量成长奖励，危险色只表达风险。

首页突出任务的具体动作和来源；信息流优先可扫描；任务详情优先步骤和完成条件；后台优先待办与可比较数据。每页明确一个主要动作，避免多个高强调按钮争夺注意。动效用于解释状态变化，不能延迟操作或制造虚假进度。

### 6.2 设计系统交付

先建立语义 token 表和映射，覆盖背景、表面、主次文字、行动、成功、警告、危险、边框、焦点与遮罩。Web CSS 与 Swift 常量由同一说明维护，是否引入自动生成在工具成本明确后决定。

保留个人主页 6pt 网格、13pt 圆角等已确认局部规则。现有通用 Theme 的间距与 12、22、30 圆角不能直接覆盖它；建立 profileGridGap、profileTileRadius 等语义局部 token，并在设计评审后决定是否推广。首发采用明确的浅色策略，系统深色设置下仍须可读，完整深色主题另排。

| 组件族 | 必须定义的内容 | 验收方式 |

### 6.3 页面设计交付顺序

第一批完成信息架构、成长引导、阶段卡、任务详情和举报状态，先于对应功能编码。第二批完成 PO 详情与分享、工具、消息状态、账号设置。第三批补后台密度、发布素材和跨端一致性。每项交付包括页面标注、文案、交互、API 字段和完整状态样例。

建议用 5 至 8 位目标学生观察可点击原型，记录是否能独立找到下一步、判断来源、完成记录和返回。以观察到的阻断问题调整布局，不仅收集喜好投票。

### 6.4 体验质量标准

Web 在 320、375、390、768、1440 px 检查导航、正文、弹窗、表格和键盘焦点，无横向意外溢出。iOS 检查最低支持版本 iOS 17 与当前运行版本、真机、安全区、Dynamic Type、VoiceOver、Reduce Motion 和主操作至少 44pt 触控区域。

普通文字对比度建议至少 4.5 比 1，大号文字至少 3 比 1，作为本项目设计验收目标。图标不单独承担含义，进度和身份不只靠颜色表达。每页验收真实数据、加载、空、失败、长文本、登录过期与权限不足。

## 7 技术方案与数据契约

### 7.1 模块职责

成长领域负责路径、阶段、任务、适用范围和完成记录；用户领域负责成长背景和资料；内容领域负责 PO 与关联攻略；治理领域负责举报和处置；消息与实时负责存储、通知和可恢复同步；分析领域只消费经过定义的业务结果。

保持一个部署单元。先补 facade 与边界测试，再渐进迁移 user、auth 等共享包；不在同一迭代同时重构全部模块与增加全部功能。跨模块通过 api 或领域事件，不直接读写对方 Mapper。

### 7.2 建议的数据增量

| 对象 | 计划补充的字段或规则 | 兼容要求 |
| --- | --- | --- |
| 成长背景 | school、major、entryYear、stageOverride 与修改时间 | 旧用户缺字段时进入待补充，不虚构值 |
| 学期日历 | 学校、学年、学期、起止日期、有效状态 | 校历缺失时退化阶段名，不计算假周次 |
| 路径与任务 | 适用范围、版本、步骤、来源、核验、有效期、关联资源 | 先增加可选字段，保留已发布旧客户端能力 |
| 完成记录 | user、task、version、方式、事件 ID、撤回状态 | 唯一约束和幂等，保留历史可追溯 |
| 举报案件 | 对象、原因、状态、处理版本、操作者、申诉关联 | 证据访问受限，用户回执与内部证据分离 |
| Outbox | 事件 ID、对象 ID、类型、负载版本、重试与状态 | 与业务同事务，支持去重与失败回查 |
| 分析事件 | 事件 ID、schema、时间、端、必要业务维度 | 白名单字段、保留期限和删除规则 |

以上是数据设计输入，字段名与拆表方式需实施时评审。先检查已有结构，避免新建平行模型。Flyway 已有 V18，新增迁移按当时最高版本递增，不修改已发布迁移。

### 7.3 API 增量规划

优先扩展现有用户资料与 Achievement API，提供当前阶段摘要、任务详情、完成及撤回、关联攻略、后台内容与举报处理接口。会话和消息提供游标端点。新端点路径在契约评审时确定，本文不把候选设计描述为已上线接口。

所有端点明确权限、请求/响应、空值、稳定错误码、幂等和分页；时间返回带偏移格式。写请求失败保留 HTTP 语义。后端 DTO 变更后生成前端类型并校验 Swift 模型；不手改 api-types.ts。iOS 旧版缺字段时有兼容行为，不能因新增字段强制崩溃。

### 7.4 身份与共享状态

为用户建立可撤销的身份版本或等效机制，覆盖 access 与 refresh 的签发、校验、改密、封禁、注销和退出所有设备。明确状态后端故障时的行为，避免为减少查询牺牲即时失效目标。Cookie 会话与用户 session 索引需要一起续期或使用不会漏掉活跃会话的索引设计。

Redis 模式必须验证跨实例；memory 模式只适合本机开发与明确的单实例测试。每类共享状态继续通过既有接口访问，不在业务里额外建一套进程 Map。

### 7.5 消息与一致性

Outbox 投递采用至少一次语义，客户端与消费者按事件 ID 或消息 ID 去重。WebSocket 序号仅作事件流续传依据，不能替代消息事实表的游标。校验保留窗外的恢复流程；重放时按权限过滤，禁止恢复已经不可见的对象。

点赞、收藏和评论计数使用原子增量、唯一事实记录与必要的重算校验；重试不能重复加数。完整列表通过稳定排序键与唯一 ID 分页。为长会话、热门帖、重复请求和并发撤回准备代表性测试数据。

## 8 数据指标与实验计划

### 8.1 事件目录

客户端记录页面与操作：landing_viewed、onboarding_completed、stage_card_viewed、task_detail_viewed、guide_opened、guide_helpfulness_submitted、tool_started、tool_exported、session_started。服务端记录结果：signup_completed、task_completion_recorded、task_completion_reverted、post_published、report_created、report_resolved。

公共字段包括 eventId、schemaVersion、occurredAt、client、appVersion、内部 userId、必要对象 ID、学校/专业/cohort 和渠道 ID。错误只带稳定错误码与 requestId。登录前后归因规则单独评审，不使用侵入式设备指纹。

事件不包含手机号、生日、性别、MBTI、星座、正文、私信、文件内容、文件名、密码、验证码或 token。帮助反馈使用固定原因枚举，自由文本留在受控业务系统。原始事件保留期、聚合保留期和注销删除规则在启用前写清楚。

### 8.2 统一指标口径

| 指标 | 计算口径 | 使用限制 |
| --- | --- | --- |
| 激活率 | 有效新注册用户在 24 小时内完成必要背景且打开适配任务的比例 | 无适配内容单独列出，不掩盖供给问题 |
| 首任务完成率 | 有效新注册用户在 7 天内至少记录一项有效任务完成的比例 | 区分自报与系统自动；排除重复与撤回 |
| D7 留存 | 注册日后第 7 个上海自然日有有效前台使用的人数除以成熟 cohort 人数 | 只统计已到观察日的 cohort，显示分子分母 |
| WAP | 本 ISO 周内新记录至少一项有效任务完成的去重用户 | 按服务端完成时间归周；排除重复、测试和截至统计时已撤回的记录，修订可追踪 |
| 内容覆盖率 | 当前阶段有有效适用攻略的关键任务数除以关键任务总数 | 关键任务清单固定版本 |
| 内容新鲜度 | 当前可见时效内容中仍在核验有效期内的比例 | 展示过期存量与待更新责任人 |
| 工具成功率 | 成功导出次数除以开始实际处理次数 | 取消单列，不能作为错误或成功 |
| 治理时效 | 创建到首次受理、创建到结案的时长及超时率 | 同时展示待处理存量与严重度 |

有效前台使用以成功打开核心页面或执行核心操作定义；后台心跳、通知到达不算回访。统一以 Asia/Shanghai 划分自然日和 ISO 周；内部测试账号在事件源和报表均标记排除。

### 8.3 实验与决策

先验证学生能否完成任务与理解信息来源，再比较阶段卡文案、入口和任务数量。每次实验预先写假设、主指标、保护指标、范围和停止条件；小样本先做观察与访谈，不宣称显著提升。

沿用 300 至 500 注册、D7 约 30%、首任务约 30%作为待检验假设。它们不能证明商业模式成立，也不是外部承诺。若任务打开多但完成少，先查步骤与场景；若激活低，先查引导和内容匹配；若回访低，先查下一阶段价值和内容供给。

## 11 人力工作量与预算

### 11.1 资源假设

参考团队配置为后端 1 人、iOS 1 人、Web 与测试工程 1 人，产品/设计和校园运营可兼职，但必须有人负责。角色名表示责任，不表示现有团队已具备这些人员。AI 可协助实现、分析和测试，需求取舍、验收、权限、内容与发布仍要明确负责的人。

每名工程师按每周 5 个工作日、70% 可投入计划工作的比例估算，三人每周总有效容量约 10.5 人日；其余用于沟通、评审、临时缺陷与外部等待。12 周容量约 126 人日，16 周约 168 人日。单一后端负责多个关键路径，不能只凭总人日判断排期可行。

24 个工作包的工程估算合计为 96 至 141 人日，中点约 119 人日。Beta 前 DP01 至 DP22 合计 89 至 130 人日，中点约 110 人日；按每周 10.5 人日，单看总量就约需 8.5 至 12.4 周。因此不能使用第 9 周之后的容量，证明第 8 周已完成全部试点准备。基线安排第 11 至 13 周进入 Beta，并留出后续观察和修复窗口。

单后端工作量偏高，S1 需按 BE、IOS、WEB 拆分重新平衡；可由具备能力的 Web/测试工程协助后端集成与报表，或增加后端资源。16 周参考窗口不消除专业分工和外部等待带来的瓶颈，超出时应顺延或裁剪范围。

若只有创始人一人兼全部工程角色，按每周 3.5 个有效工程日计算，仅工程工作就约需 28 至 41 周，内容、研究和外部等待另计。可先拆出 2 至 3 周的内部 Alpha 切片，但不能把完整试点范围压成同样工期。

### 11.2 角色职责

| 角色 | 负责结果 | 主要验收责任 |
| --- | --- | --- |
| PO 产品负责人 | 范围、优先级、试点对象与关键取舍 | 用户任务、发布范围和阶段是否进入 |
| DS 设计 | 架构、页面、组件、文案与可用性 | 视觉层级、状态完整、无障碍与体验 |
| BE 后端 | 契约、模型、权限、并发、消息与状态 | 数据一致、故障恢复、跨实例与性能 |
| IOS 工程 | 原生流程、本地工具、Keychain 与发布 | 最低系统、真机、签名、通知与交互 |
| WEB 工程 | 分享、响应式、后台与契约消费 | 链接可访问、窄屏、Cookie 与后台效率 |
| QA 测试责任人 | 用例、自动化、回归和证据 | 严重缺陷、端到端旅程与回归覆盖 |

允许同一人承担多个角色，但每个工作包只设一位最终负责人。真实安全、隐私、协议和发布事项由有相应权限的负责人签收，不由自动化测试替代。

### 11.3 预算模型

开发预算按各角色确认的人日乘实际费率计算；基础设施按应用、MySQL、Redis、对象存储、备份、流量、日志监控、邮件或短信分别列账；运营预算按核验内容、学生访谈、合作交付和招募活动计。开发者账号与分发服务按真实账单纳入，不在规划中虚构价格。

S1 给出预算上限、月度运行上限和试点招募上限。每周看成本与已交付结果，新增工具、附件、推送通道或商业服务前先核算单位成本与取消方式。没有学校、渠道和预算信息时，不锁定付费推广金额。

## 12 测试发布与运维计划

### 12.1 验证分层

后端覆盖规则、边界与幂等单测，以及真实 MySQL/Redis 的会话、事务、分页、并发和迁移集成测试。Web 使用构建、lint、类型契约与核心旅程自动化；iOS 使用编译、模型/状态测试、UI 冒烟、真机和最低系统验证。目前没有 iOS XCTest target 和 CI 构建 job，应在 DP21 补齐，不把现有 CI 绿解释为 iOS 已验证。上传和文件本地处理单独验证。

复用仓库已有检查：前端 lint/build、后端测试、shell 语法、Compose 配置、smoke.sh 和生成类型差异检查。只改文档时检查内容、链接与排版即可；功能提交按影响执行完整检查。测试数量随代码变化，不把旧文档的固定数量当质量证明。

| 场景组 | 必测样例 | 通过条件 |
| --- | --- | --- |
| 身份 | 旧 token、Cookie、改密、封禁、注销、双实例 | 旧身份按规则拒绝，无跨设备遗漏 |
| 成长 | 不同背景、无校历、无匹配、撤回、路径变更 | 阶段与分母正确，历史不丢失 |
| 内容 | 长文、多图、上传失败、拉黑、下架 | 权限与状态一致，失败不丢草稿 |
| 消息 | 回滚、进程退出、重试、断线、保留窗外 | 最终消息可恢复，无重复展示 |
| 治理 | 重复举报、并发处置、越权、申诉 | 状态可追溯，私密证据不外泄 |
| 工具 | 大图、多图、离线、取消、导出失败 | 结果可用，文件不上传，失败可解释 |
| 展示 | 窄屏、大字体、键盘、VoiceOver、系统深色 | 主要操作可达，文本可读 |

### 12.2 发布流程

按开发、集成/预发布、封闭试点区分数据与配置。CI 产物记录 commit、迁移版本和客户端版本。Release 使用 HTTPS API 地址、正确签名和通知配置；不能沿用 localhost、开发 entitlement 或全局禁止签名设置。

发布前先备份，再验证兼容迁移、配置和健康检查；先受控小范围，观察错误、任务、举报和消息指标。回滚优先回退应用版本与关闭功能；已执行迁移不通过修改旧 SQL 回退，需评估兼容与前向修复。每次发布留负责人、版本、检查证据和回退步骤。

### 12.3 恢复与告警

试点建议目标为 RPO 不超过 24 小时、RTO 不超过 4 小时，含义分别为可接受的数据丢失窗口与恢复耗时；这两个值是待演练确认的内部目标。备份必须包含数据库、媒体对象、对象引用关系和必要配置恢复说明，敏感配置单独受控保管。

至少完成一次异机或隔离环境恢复，抽查登录、帖子、任务进度、消息和媒体。关注 HTTP 错误与延迟、DB 连接、Redis、Outbox 积压、WS 断线、推送失败、磁盘和备份失败。requestId 用于日志定位，不作为指标标签。

### 12.4 性能基线

DP23 在固定机器规格、代表性数据和明确压测脚本下记录吞吐、P95、错误率、DB/Redis 与内存。首轮可用的试验负载建议为持续 30 分钟、读写混合 50 请求每秒及 200 条 WS 连接；读接口 P95 500ms、写接口 P95 800ms、服务端错误率低于 1%作为待测预算，不含大文件和第三方耗时。

这些数字只用于建立可复现的第一条基线，不是已达到能力，也不代表百万日活容量。首次结果出来后由团队确认 SLO 与试点上限，再决定索引、缓存、图片直传、CDN 和扩容优先级。

## 13 内容运营与试点执行

### 13.1 内容准备

优先选能找到真实学生、可靠作者和核验人的学校与专业。先访谈 5 至 10 位高年级作者及目标学生，确认当前阶段的问题。首批准备一条主线与约 30 至 50 条有效本地内容，每个关键任务至少有一份可执行攻略；内容数量服从覆盖与质量。

内容模板包含问题、适用对象、步骤、完成条件、来源、核验人、核验日、复核日和关联任务。校园运营核实学校差异，平台负责人审核主线。未获得官方授权的内容标为运营整理或学生经验，不使用官方身份宣传。

### 13.2 治理值守与交接

试点前确认举报与紧急撤内容的实际值守人和替补。建议一般举报在一个工作日内首次处理，高风险内容在实际值守时段内优先响应；具体时限由人员覆盖确认后公布，不作无人值守的全天承诺。

运营每天看举报积压与临近过期内容，工程值班负责 Outbox 与服务告警的技术响应，运营协调用户沟通；每周共同复盘主线缺口、帮助反馈、渠道质量与申诉。账号、作者授权、合作联系人、权限和未完事项归平台受控记录，换届时逐项交接。

### 13.3 招募与复盘

先邀请 30 至 50 名学生观察真实任务，访谈中允许明确说不适用或没帮助。渠道码记录来源，不记录敏感身份材料。推广文案只描述已开放功能，用户可以先读攻略，不强制下载。

每周复盘激活、首任务、成熟 D7、WAP、内容覆盖、工具成功、举报时效和访谈。选择两到三个具体问题进入下一迭代，例如学校选择无结果、任务步骤不清、分享后找不到原文。避免把低留存直接归因于奖励不足。

### 13.4 复制条件

至少完成两个成熟 cohort 的观察与治理复盘，说明留存、任务价值和供给是否持续。第二学校应通过配置、模板、内容导入与权限分配接入；如果还需改多处学校常量，先修复制能力再推广。商业化与 Android 另立项目范围评估。

## 16 验收记录与分析追溯

### 16.1 单项完成标准

一项工作完成需同时具备真实数据/API、权限与异常处理、设计状态、必要测试、相关文档和验收证据。证据写入工作包记录：构建与测试结果、截图或录像路径、迁移及契约变更、运营操作步骤、残留风险和验收人。

接口完成但客户端未接、UI 完成但仍假数据、举报能提交但无人处理、文件能生成但不能导出，都不能标为用户功能完成。纯技术修复可单独关闭，但需写清不等于关联产品功能已完成。
